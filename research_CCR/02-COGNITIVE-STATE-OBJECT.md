## 0. Executive Summary

This document specifies the **Cognitive State Object (CSO)** at field level: the persistent, versioned, provenance-complete data structure that holds everything a CCR agent has learned. Document 00 argued that an agent's cognitive state must become an explicit object rather than an invisible amalgam of prompts and databases; document 01 gave the object its formal definition as a 14-component tuple governed by five invariants. This document answers the question an implementer actually asks: *what are the fields, what are their types, what do the invariants require of them, and what operations are legal on the result?*

Three design commitments shape everything below. First, **every content item carries its own provenance**: borrowing the vocabulary of W3C PROV-O, each learned artifact is an *Entity* generated by an *Activity* (a learning transaction) associated with an *Agent* (the CCR identity), linked by `wasDerivedFrom` to the experiences that justify it ([PROV-O](https://travesia.mcu.es/bitstream/10421/7484/1/PROV-O.pdf)). Second, **all addressing is content-based**: like IPFS/IPLD Merkle-DAG structures, every object is identified by the hash of its canonical serialization, so references are tamper-evident by construction and the state DAG falls out of the addressing scheme rather than being bolted on ([content-addressable storage](https://hal.science/hal-02559031v1/file/content-addressable-storage-preprint.pdf)). Third, **the schema is mechanism-neutral**: it constrains what must be *true* of skills, policies, and memories (their metadata, lifecycle, and provenance), not how they are *represented* (code, weights, or natural language).

## 1. Design Requirements

The CSO schema is derived from seven requirements, each traceable to a design principle in document 00. **R1 — Completeness:** the object must hold everything that conditions behavior (P1), so that "the agent's state" is one serializable thing. **R2 — Typed heterogeneity:** memory, skills, policies, and causal structure have different shapes and lifecycle rules; the schema must distinguish them (P3). **R3 — Versioned everything:** every component participates in the commit/version/rollback semantics of the state DAG (P6). **R4 — Provenance completeness:** every item traces to experiences and transactions (invariant I4), which the schema must make structurally mandatory rather than conventionally encouraged. **R5 — Confidence as a first-class field:** every learned item carries confidence from its grounding evaluations (§5 of document 01). **R6 — Enforceable invariants:** invariants I1–I5 must be mechanically checkable over the schema, not merely stated about it (Obligation 7.4). **R7 — Serialization neutrality:** the logical schema must admit multiple physical encodings (JSON-LD for interoperability, a binary columnar form for hot-path retrieval) without semantic change.

A consequence worth stating before any fields are introduced: **the schema has no write-once convenience paths.** The temptation in implementation is to allow the runtime to scribble directly into state ("just update this counter"), bypassing transactions; every such path silently voids invariants I4 and I5 and the provenance guarantee. The schema therefore distinguishes *fields* (which exist) from *mutation authority* (which belongs exclusively to the Learning Transaction machinery of document 04). The CSO is a read-mostly object: read constantly on the hot path, written only by commits.

## 2. Top-Level Structure

### 2.1 The object

```text
CognitiveStateObject
├── header                    identity, version, lineage anchors
├── semantic_memory           facts, concepts, consolidated knowledge
├── episodic_index            pointers into the experience ledger
├── procedural_skills         executable procedures + metadata
├── policy_table              context-conditioned strategy distributions
├── strategy_library          named strategy definitions
├── goals                     persistent goal stack
├── preferences               learned preference parameters
├── confidence_map            content → confidence assignment
├── causal_graph              typed, weighted causal structure
├── evaluation_history        evaluator calibration + verdict summaries
├── provenance_index          item → derivation path index
└── lineage                   parent refs, commitment, signature
```

The ordering is not arbitrary: components are grouped by *consumer*. The hot path reads `semantic_memory`, `episodic_index`, `procedural_skills`, `policy_table`, `strategy_library`, and `confidence_map` during context assembly; the Learning Engine reads and proposes against everything; the trust layer reads `header`, `provenance_index`, and `lineage`. Grouping by consumer keeps the read paths for the latency-critical hot loop free of provenance-resolution overhead — provenance is resolved lazily, only when an audit, a validation, or a merge requires it.

### 2.2 Header

```json
{
  "cso_id":      "cso:sha256:…",            // content hash of this object minus lineage.signature
  "agent_ref":   "did:gns:…",               // identity record reference (Document 01, Def. 10.1)
  "model_ref":   {"family": "…", "version": "…"},
  "version":     8921,
  "created_at":  "2026-09-06T…Z",
  "parents":     ["cso:sha256:…"],          // 1 for commit/branch, 2 for merge
  "update_ref":  "tx:sha256:…",             // the learning transaction that produced this state
  "schema_ver":  "ccr-cso/0.1"
}
```

Three header fields carry the security-critical load. `cso_id` is content-addressed: because it is the hash of the object's canonical form, any mutation to any field anywhere in the object changes the identifier, which is the mechanism that makes Definition 8.1's commitment chain self-verifying rather than trust-based ([CID/IPLD design](https://easierdata.org/updates/2024/2024-01-25-getting-to-know-content-addressable-archives)). `parents` makes the DAG structure explicit in the object itself — a merge state has two parents, and the graph is traversable from any node without an external index. `update_ref` binds each state to exactly one learning transaction, which is what makes the provenance property `CommittedUpdate ⇒ ValidatedExperience` checkable by following a single pointer.

## 3. Component Schemas

### 3.1 semantic_memory

Semantic memory stores decontextualized knowledge: facts, concepts, domain relationships, and consolidations distilled from episodes. The unit is the **memory item**:

```json
{
  "id":          "mem:sha256:…",
  "type":        "fact | concept | relation | consolidation",
  "content":     { "text": "…", "embedding_ref": "emb:…" },
  "scope":       { "domains": ["…"], "valid_context": "…" },
  "confidence":  0.87,
  "sources":     ["exp:sha256:…", "exp:sha256:…"],
  "supersedes":  "mem:sha256:…",
  "status":      "active | deprecated | contested",
  "created_tx":  "tx:sha256:…",
  "last_confirmed_tx": "tx:sha256:…"
}
```

Two fields distinguish this from a conventional vector-store entry. `sources` is mandatory and non-empty for learned items: a semantic memory that cannot name the experiences it came from violates I4 and cannot be committed. `sources` is also what makes **support independence (I6, doc 01 Def. 7.4a)** enforceable: because a consolidation names its root experiences, a later consumer can dedupe — a fact consolidated from a policy's own evidence contributes **no independent support** to that policy beyond the shared `sources`; support is counted over the union of root `exp_id`s, never summed across the policy and the fact. `supersedes` implements belief revision as *graph extension rather than mutation* — a corrected fact does not overwrite its predecessor but points at it, preserving the full history of what the agent believed, which is exactly what rollback (Definition 8.4) and drift measurement (§12 of document 01) require. Items of `type: consolidation` are the schema's answer to ledger growth: they summarize a set of raw experiences (named in `sources`) into reusable knowledge, in the spirit of the trajectory-to-event consolidation that LongMemEval-V2 showed to outperform raw-slice retrieval ([LongMemEval-V2](https://arxiv.org/html/2605.12493v1)), while the raw experiences remain addressable in the ledger.

The `status` field carries a third value, **`contested`**, for the case that `supersedes` cannot express: two active items whose contents contradict each other, where the system has *detected* the contradiction but has *not* — and must not — decide which one is true. `supersedes` is a directed, resolved relation — a corrected fact points back at the predecessor it replaces. A contradiction found in the field is not yet a correction: the evidence has not established which item is the error. When contradiction detection (the consolidation-time and commit-time check over semantic memory) finds a conflicting pair, it marks **both** items `contested` rather than superseding either. A contested item is **present in state but not behavioural**: it is retained, addressable, and diffable, but it does not feed a decision — exactly the treatment the confidence-floor already gives a below-floor item at read time (§3.6). `contested` reuses that non-behavioural read-time semantics rather than introducing a second suppression mechanism; the read path already knows how to hold an item without acting on it. It also mirrors the `pending` state of the episodic_index (§3.2): a captured-but-not-yet-gated experience is likewise present and non-behavioural while it awaits a decision. A contested pair stays contested until *new evidence* resolves it (a later transaction supersedes one item, clearing the other's contested mark) or a *human* resolves it.

The prohibition is normative: **the system MUST NOT auto-resolve a contradiction by confidence.** Demoting the lower-confidence item and keeping the higher looks like a natural tie-break, but it optimizes for the wrong thing — a well-attested falsehood would demote a poorly-attested truth. Confidence measures how much corroboration an item has accumulated, not whether it is correct; letting it settle contradictions rewards *agreement* over *correctness*, and does so silently, erasing the true item with no record that a conflict ever existed. Detection's only authority is to *mark* the conflict (making both non-behavioural, so neither drives a decision on stale ground); *resolution* requires evidence or a human, and until one arrives the contested pair is the honest state — "these two beliefs cannot both hold, and I do not yet know which fails." Human resolution of a contested pair is a **two-actor decision** — a person adjudicates a belief the system holds — and therefore belongs in a **`cgr.cosign.v1`** co-signature envelope (`grafomem/docs/cgr/cgr-cosign-v1-spec.md`), *not* a free-text `resolved_by` field. This is the same finding recorded against doc 04's superseded `validation.human_approval`: an unsigned human decision recorded as plain data is unattributable and strippable; a contested-pair resolution carries the same weight as a high-risk learning approval and takes the same envelope.

### 3.2 episodic_index

The episodic index is **not** the experiences themselves — those live immutably in the ledger (document 01, §4.2) — but a versioned *view* over them:

```json
{
  "incorporated":  ["exp:sha256:…"],          // grounding set of this state
  "rejected":      [{"exp": "…", "reason": "…", "tx": "…"}],
  "pending":       ["exp:sha256:…"],          // captured, not yet gated
  "indexes":       {"by_goal": "…", "by_outcome": "…", "by_cause": "…"}
}
```

This component makes the grounding relation of document 01 (§4.2) a stored, diffable structure rather than a derived query: auditing a state means reading its `incorporated` set and checking each element's validation record, and diffing two states means set operations on `incorporated`. The `rejected` list is first-class for the reason given in the admission-function design (document 01, §6): rejected experiences must remain research-visible, including *why* they were rejected, because the admission function's false negatives are recoverable only if the rejection record survives.

### 3.3 procedural_skills

Skills are executable procedures — the L2 content of the taxonomy. The unit is the **skill record**:

```json
{
  "id":           "skill:sha256:…",
  "name":         "resolve-api-rate-limit",
  "version":      3,
  "kind":         "workflow | tool_macro | code | policy_fragment",
  "trigger":      { "context_pattern": "…", "goal_types": ["…"] },
  "body_ref":     "blob:sha256:…",            // executable content, content-addressed
  "interface":    { "inputs": ["…"], "outputs": ["…"], "tools": ["…"] },
  "granularity":  "subtask | task | episode",
  "usage":        { "invocations": 41, "successes": 36, "last_used": "…" },
  "confidence":   0.78,
  "derived_from": ["exp:sha256:…"],
  "composed_of":  ["skill:sha256:…"],
  "status":       "active | deprecated | shadow",
  "created_tx":   "tx:sha256:…"
}
```

The schema encodes four lessons from the literature. `body_ref` is content-addressed and separate from metadata, because skill bodies can be large (code, workflow graphs) and the hot path usually needs only `trigger`, `interface`, and `confidence` for selection — the same progressive-disclosure argument made for structured tool descriptions in the MCP literature ([MCP tool descriptions](https://arxiv.org/html/2602.14878v3)). `granularity` is explicit because AWM's central finding was that sub-task-granular induced workflows generalize where task-level ones overfit ([AWM](https://arxiv.org/abs/2409.07429)); making granularity a field rather than an accident lets the Skill Manager enforce a granularity policy. `usage` exists because skills must be *deprecatable* — Memento's small-curated-bank result ([Memento](https://arxiv.org/html/2508.16153v2)) and Soar's utility problem both say unbounded skill accumulation eventually harms retrieval and selection. `status: shadow` gives candidate skills a first-class pre-commit existence, matching the validation topology of the learning transaction.

### 3.4 policy_table

The policy table is the L3 content: context-conditioned distributions over strategies (document 01, §4.3).

```json
{
  "context_model": { "classifier_ref": "…", "regions": ["…"] },
  "entries": [
    {
      "region":        "api-interaction/rate-limited",
      "distribution":  {"strategy:retry-backoff": 0.72, "strategy:queue-defer": 0.28},
      "confidence":    0.81,
      "evidence":      {"supporting": ["exp:…"], "counter": ["exp:…"]},
      "causal_basis":  ["cg-edge:…"],
      "updated_tx":    "tx:…"
    }
  ],
  "default_policy": "uniform",
  "risk_class":    "medium"
}
```

The two fields that carry CCR's thesis are `causal_basis` and `evidence.counter`. `causal_basis` implements the admissibility requirement of document 01 (§9): a policy entry must cite the causal-chain edges that justify it, or it cannot pass validation. `evidence.counter` stores *disconfirming* experiences alongside confirming ones, so the entry represents a state of evidence rather than a verdict — the schema-level defense against the deterministic-memory critique (BeliefMem) that motivates the whole confidence-carrying design. `risk_class` on the table (and optionally per-entry) drives the authorization guard: entries whose strategy distributions license high-blast-radius actions are classified `high`, and any update to them routes through human approval per the validation predicate of document 01 (§7.5).

### 3.5 strategy_library, goals, preferences

These three components are deliberately simple records that the more complex machinery references. `strategy_library` holds named strategy definitions — the `𝒰` of the formal model — each with a description, preconditions, expected-cost model, and provenance; policies assign probabilities to strategy IDs, not to inline definitions, keeping the policy table small and the strategies reusable across regions. `goals` is a persistent goal stack with per-goal status, priority, and provenance (a goal learned from a delegation event carries its mandate reference; a goal inferred from experience carries its experience reference — the distinction matters for I5). `preferences` holds learned preference parameters (verbosity, risk posture, tool aesthetics) as a flat map with per-key confidence and provenance; it is the lowest-risk component and the natural place for the experimental program to begin, since preference updates exercise the full transaction machinery at minimal blast radius.

### 3.6 confidence_map

The confidence map is the single authoritative assignment `conf : Content → [0,1]` required by invariant I3, implemented as a separate index rather than only as per-item fields:

```json
{
  "items":   { "mem:…": 0.87, "skill:…": 0.78 },
  "default": 0.5,
  "policy":  { "floor_commit": 0.55, "decay_rate": 0.001, "decay_clock": "commits" }
}
```

Duplication of confidence (on items *and* in the map) is intentional denormalization: per-item fields serve the hot path, the map serves global queries ("all content below the commit floor"), and I3 includes the requirement that the two agree. The `decay_rate` field deserves comment: confidence that is never re-confirmed should decay, because the environment is non-stationary and yesterday's validated strategy may be today's obsolete one. Decay is *not* a silent mutation — it is computed at read time from `created_tx`/`last_confirmed_tx` and the decay policy, so the stored object stays immutable and the decay policy itself is versioned state. This is the schema-level resolution of a tension the roadmap names (cognitive drift): beliefs fade unless re-earned, and the fading rule is itself auditable.

### 3.7 causal_graph

```json
{
  "nodes": [ {"id": "cg:…", "type": "goal|strategy|action|outcome|cause|learning", "ref": "exp:…|skill:…"} ],
  "edges": [ {"id": "cg-edge:…", "rel": "motivates|selected|produced|attributed-to|replaced-by|validated-into",
              "from": "cg:…", "to": "cg:…", "confidence": 0.74,
              "attributed_by": "evaluator|agent-trace|human", "created_tx": "tx:…"} ]
}
```

The graph is stored inside the CSO (it is versioned state) but its nodes are *references* into the ledger and skill library (which are not), respecting the separation of document 01 §4.2. The `attributed_by` field on every edge is the schema's honesty mechanism: causal edges are claims with sources, and an edge attributed by the agent's own trace carries different evidentiary weight than one attributed by an independent evaluator — the difference being expressible in `confidence` and queryable during validation. The full causal machinery, including chain semantics and counterfactual query patterns, belongs to `05-CAUSAL-COGNITIVE-GRAPH.md`; this document fixes only the storage contract.

### 3.8 evaluation_history

```json
{
  "channels": [ {"id": "unit-tests", "reliability": 0.97, "verdicts": 1204},
                {"id": "lm-critic",  "reliability": 0.71, "verdicts": 3411} ],
  "recent_verdicts": "ring-buffer ref",
  "calibration_tx":  "tx:…"
}
```

This component is the L4 (meta-learning) foothold at schema level: the evaluator's per-channel reliability estimates are *state*, updated through transactions, and consumed by the admission function's trust term. Storing verdict counts alongside reliability exposes the estimator's support — a channel with reliability 0.71 over 3,411 verdicts is a different object than one with 0.71 over 12 — and the admission function is expected to use the pair, not the point estimate.

**What reliability is measured against (operationalized 2026-09-07).** The paragraph above says reliability is *updated through transactions* — a mechanism — but does **not** name what a verdict is scored *against*. It is scored against a **designated reference channel** trusted for reasons extrinsic to the system (doc 07 §2.2a): reliability is the channel's agreement rate with that reference, so the `(reliability, verdicts)` pair the trust term consumes is **only as meaningful as the reference is trustworthy**. This has a hard consequence for the schema: **`reliability` is well-defined only where the deployment has such a reference** — a domain that produces delayed, independent, outcome-grounded signals (tests, confirmed outcomes, a vetted oracle). Where none exists (the AML case, `Ulissy-s-r-l/eu-governed-agent` ADR-0009), the calibration column is **undefined, not zero**: reliability cannot be established at all, and a consumer MUST NOT read a default/self-reported value as if it were calibrated. See doc 07 §2.2a for the full limit and its identity-assurance parallel (gap 3a).

### 3.9 provenance_index and lineage

The provenance index is the materialization of I4:

```json
{
  "index": { "skill:…": {"tx": "tx:…", "experiences": ["exp:…"], "derivation": "direct|consolidated|merged"} }
}
```

Every content item in the object appears in this index, and every index entry resolves to a transaction whose validation record names experiences — that chain being exactly the PROV-O pattern `Entity ← wasGeneratedBy ← Activity ← wasAssociatedWith ← Agent` with `used` pointing at the experiences ([PROV-O](https://travesia.mcu.es/bitstream/10421/7484/1/PROV-O.pdf)). The `lineage` block closes the object:

```json
{
  "commitment": "cso:sha256:…",            // = header.cso_id, bound with update + validation refs
  "validation_ref": "val:sha256:…",
  "signature": "sig:gns:…",                 // identity-layer signature over the above
  "genesis_ref": "cso:sha256:…"
}
```

With `lineage` present, the object is **self-certifying**: given nothing but the serialized CSO and the identity layer's public key, a verifier can check that this state was committed by a validated transaction under a known identity, and can begin walking `header.parents` to reconstruct the full chain to `genesis_ref`. This is the property that makes the document-00 claim — the agent as a verifiable history of state transitions — a property of the data structure itself rather than of any surrounding service.

## 4. Invariants Made Mechanical

The five invariants of document 01 (Definition 7.3) are restated here as the checks the Cognitive State Manager must run at commit time, with their failure modes:

| Invariant | Mechanical check over this schema | Typical failure caught |
| --- | --- | --- |
| **I1 referential integrity** | Resolve every `*_ref`, `sources`, `derived_from`, `composed_of`, `causal_basis`, and `parents` pointer; all must exist and hash-match | Dangling citation after a merge; tampered body blob |
| **I2 normalization** | Every `policy_table.entries[].distribution` sums to 1 ± ε; regions are disjoint or have a defined precedence | Botched policy reweight after merge |
| **I3 confidence coherence** | Every item confidence ∈ [0,1]; item fields agree with `confidence_map`; commit floor respected for `status: active` | Stale confidence after rollback |
| **I4 provenance completeness** | Every content item has a `provenance_index` entry whose transaction resolves to a validation record citing ledger experiences | Direct (untransacted) write to state |
| **I5 authority consistency** | Static analysis of `policy_table` + `procedural_skills` payloads against `agent_ref`'s current authority scope | Skill licensing an out-of-scope tool |

Two properties of this table matter for implementation. First, every check is **deterministic and cheap** relative to the learning pipeline — no model calls, only pointer resolution, arithmetic, and static analysis — so invariant checking can sit unconditionally on the commit path (Obligation 7.4) without becoming the latency bottleneck. Second, the checks are **complete with respect to direct writes**: any state mutation that bypassed the transaction machinery breaks I4 by construction, which means invariant checking doubles as tamper detection, complementing (not replacing) the cryptographic detection in the commitment chain.

## 5. Lifecycle and Legal Operations

The CSO admits exactly six operations, all but the first routed through learning transactions:

1. **`read(query, version?)`** — hot-path and audit access; reads are the only operation that never touches the transaction machinery, and they are version-pinned so that a shadow validation reads exactly the state it claims to validate.
2. **`propose(ΔC)`** — construct a candidate state `Ĉ = C ⊕ ΔC`; pure, side-effect-free, and permissionless (any component may propose).
3. **`commit(ΔC, validation_record)`** — the only writer; requires the guards of document 01 §7.2; produces a new object with incremented `version`, extended `parents`, and sealed `lineage`.
4. **`branch(C_n, {ΔC^A, ΔC^B})`** — two commits from one parent; first-class because shadow policies and A/B cognition are designed uses, not hacks.
5. **`merge(C_a, C_b)`** — a commit with two parents whose update reconciles the two diffs; the weakest-specified operation, flagged in document 01 as an open problem, with conflict semantics deferred to implementation experience in Phase 6.
6. **`revert(C_n, C_k)`** — a forward commit whose content equals the ancestor's, per Definition 8.4; history is never rewritten.

The deliberate omissions are as important as the list: there is **no `update-in-place`, no `delete`, and no field-level setter.** Content items are deprecated (status flip, via transaction) rather than deleted; corrections are supersessions rather than edits; the ledger is untouched by all of it. This is what the "read-mostly object" requirement of §1 means operationally, and it is the schema's enforcement of the transactional design principle P2.

## 6. Serialization and Interoperability

The canonical interchange encoding is **JSON-LD with a CCR context** mapping provenance terms onto PROV-O (`wasDerivedFrom` for `sources`/`derived_from`, `wasGeneratedBy` for `created_tx`, `Agent`/`actedOnBehalfOf` for the identity and delegation references), so that a serialized CSO is a valid PROV-O bundle and standard provenance tooling can traverse it ([PROV-O](https://travesia.mcu.es/bitstream/10421/7484/1/PROV-O.pdf)). Canonicalization for hashing follows the IPLD discipline — deterministic field ordering, no whitespace dependence, hashes computed over the canonical form — which is what makes `cso_id` stable across implementations and languages ([content-addressable storage](https://hal.science/hal-02559031v1/file/content-addressable-storage-preprint.pdf)). Large bodies (skill code, embeddings, workflow graphs) live outside the JSON envelope as content-addressed blobs referenced by `*_ref`, keeping the object itself small enough that hashing and diffing stay cheap.

For the hot path, a binary columnar encoding of the read-side components (memory, skills, policies, confidence) is permitted as a derived artifact — derived, meaning it is regenerated from the canonical object at commit time and carries the same `cso_id`; it is a cache, never a source of truth. This split mirrors the read/write asymmetry of the whole architecture: the write path is rare, transactional, and pays full provenance costs; the read path is constant, latency-critical, and pays only retrieval costs.

## 7. Summary and Handoff

The CSO specified here is a self-describing, self-certifying, versioned graph of typed learning artifacts in which every item knows what it is, how confident the system should be in it, what experiences produced it, and what transaction committed it. The schema decisions that carry the research thesis are four: provenance is a structural field, not a log; confidence is a first-class, decaying, versioned quantity; supersession replaces mutation everywhere; and the object's own hash chain makes it independently verifiable. Documents 03 and 04 build directly on this foundation: `03-EXPERIENCE-LEDGER.md` specifies the `exp:` objects this schema references, and `04-LEARNING-TRANSACTION.md` specifies the `tx:` objects that alone are allowed to change it.
